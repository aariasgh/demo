# E6-S6: Pruebas de Accesibilidad End-to-End (WCAG AA)

**Story ID**: 6.6  
**Sprint**: E6 (Epic 6: UX/UI, Responsivo y Accesibilidad)  
**Status**: ✅ PATCH APPLIED
**Points**: 8  
**Priority**: P2  
**Duration**: 3-4h estimadas

---

## Executive Summary

**Objetivo**: Validar todas las funcionalidades de accesibilidad implementadas en E6-S3 mediante pruebas automatizadas end-to-end con Playwright y auditorías de accesibilidad WCAG AA.

**Valor de Negocio**: 
- Garantizar cumplimiento WCAG AA en todos los flujos de usuario
- Prevenir regresiones de accesibilidad en futuras versiones
- Validar usabilidad de teclado (11 shortcuts) y lectores de pantalla
- Demostrar conformidad para auditorías de accesibilidad

**Dependencias**: 
- Depende de E6-S1 a E6-S5 (todas las features de accesibilidad implementadas)
- No bloquea otros epics
- Puede ejecutarse en paralelo con E7/E8

---

## User Story

**Como** QA Engineer enfocado en accesibilidad,  
**Quiero** validar que toda la aplicación cumple con WCAG AA mediante pruebas automatizadas,  
**Para** garantizar que usuarios con discapacidades (visuales, motoras, cognitivas) puedan usar la CRM sin barreras.

## Strategy de Pruebas

### Phase 1: Automated Tests (Playwright + axe-core)
1. Install `@axe-core/playwright`
2. Create test file: `frontend/e2e/accessibility.spec.ts`
3. Test coverage:
   - Initial page load + axe scan
   - KanbanBoard loaded + axe scan
   - CreateLeadModal opened + axe scan
   - QuickNotesModal opened + axe scan
   - QuickStatusModal opened + axe scan
   - RiskWidget toggled + axe scan
   - SearchFilterHeader focused + axe scan
4. Assert: 0 violations (critical/serious), log warnings
5. Run: `pnpm exec playwright test --grep "accessibility"`

### Phase 2: Keyboard Navigation (Manual + Recorded)
1. Create test cases for each of 11 shortcuts
2. Test focus trap in modals (Tab circular, Escape closes)
3. Test arrow navigation in Kanban (columns + leads)
4. Test Tab cycling through page regions
5. Document: screenshot per shortcut, console output

### Phase 3: Screen Reader Testing (NVDA)
1. Start NVDA
2. Open app in Chrome/Firefox
3. Navigate with NVDA:
   - Virtual Cursor + Browse Mode (read all elements)
   - Focus Mode + keyboard (keyboard navigation)
4. Verify: All interactive elements announced
5. Log: Issues found, NVDA output

### Phase 4: Visual Validation (Contrast, Focus)
1. Lighthouse audit (DevTools)
2. WAVE browser extension scan
3. Focus outline visibility at normal + 200% zoom
4. Color contrast check (all text + UI)
5. Document findings

## Dev Notes

### Strategy Overview
This story validates that all accessibility features implemented in E6-S1 through E6-S5 meet WCAG 2.1 Level AA compliance through automated testing (Playwright + axe-core) and manual verification (keyboard, screen reader, visual).

### Key Architectural Patterns
1. **Focus Trap**: FocusTrap component around modals (E6-S3 pattern)
2. **ARIA Roles**: role="dialog" for modals, role="region" for sections, role="alert" for errors
3. **Keyboard Context**: useKeyboardNavigation hook routes shortcuts to correct handlers
4. **Semantic HTML**: header/main/section/article elements for screen readers
5. **Spanish Localization**: aria-labels and keyboard hints in Spanish

### Testing Approach
- **Phase 1-2**: Automated tests with Playwright (CI/CD compatible)
- **Phase 3-4**: Manual testing (keyboard, screen reader, visual)
- **Phase 5**: Regression suite to ensure no accessibility regressions

### Known Considerations
- Lazy-loaded modals (E6-S5) may show 500ms spinner on first load → Plan axe scans after content loads
- Pre-existing test failures (64 tests) are unrelated to E6-S6 → Exclude from coverage count
- NVDA requires Windows + installation → Can substitute WAVE browser extension if unavailable
