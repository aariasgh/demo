## 📖 Historia de Usuario

**Como** usuario con discapacidad (visual, motora, cognitiva) o que usa tecnología asistiva  
**Quiero** usar el Mini CRM con keyboard, screen reader, y sin depender del color  
**Para que** todos en la organización puedan acceder sin barreras al sistema de ventas  

### Problema que Resuelve

- **Exclusión digital:** Usuarios con discapacidad no pueden usar la app → violación de derechos + riesgo legal (ADA/WCAG)
- **Dependencia del mouse:** Power users con lesiones RSI no pueden trabajar si falta teclado
- **Screen readers silenciosos:** Usuarios ciegos oyen "button" sin contexto → no saben qué botón es
- **Color como único indicador:** "El lead rojo está en riesgo" → usuarios daltónicos no ven el riesgo
- **Focus invisible:** Tab navigation no muestra dónde estoy → confusión total
- **Internacionalización ad-hoc:** Textos en español hardcodeados → difícil mantener, traducir

### Valor de Negocio

- **Cumplimiento Legal:** WCAG AA es estándar en LA (aunque no obligatorio, es mejor práctica)
- **Inclusión:** CRM accesible = más usuarios potenciales = mayor adopción
- **Profesionalismo:** Accesibilidad = percepción de producto maduro
- **Retención de talento:** Empleados con discapacidad pueden contribuir sin fricciones
- **Marketing:** "Accesible por defecto" es diferenciador en propuestas

### Contexto Técnico

**Qué ya existe (E6-S1 + E6-S2):**
- ✅ Responsive design (mobile, tablet, desktop)
- ✅ Animaciones suaves (fade-in, transitions, prefers-reduced-motion)
- ✅ Loading/error states con feedback visual
- ✅ Colores con cierta estructura (status: Nuevo=blue, etc.)
- ✅ React components con TypeScript

**Qué falta (E6-S3):**
- ❌ ARIA attributes (labels, roles, live regions)
- ❌ Keyboard navigation (Tab order, focus trap, Escape to close)
- ❌ Focus styling (visible outlines, high contrast)
- ❌ Semantic HTML (headings, lists, form grouping)
- ❌ Screen reader testing (NVDA/JAWS)
- ❌ Contrast validation (WCAG AA 4.5:1 texto)
- ❌ i18n base layer (string externalization)

### **GROUP 1: Focus Management & Keyboard Navigation**

```gherkin
Feature: Focus Management & Keyboard Navigation
  
  Background:
    Given que la aplicación Mini CRM está abierta
    And todos los elementos interactivos están presentes
  
  Scenario: Focus outline visible
    Given que presiono Tab
    When un elemento recibe focus
    Then aparece un outline visible
    And el outline tiene color diferente al fondo
    And el outline tiene mín 2px de ancho
    And el color es blue-500 (Tailwind focus:outline-blue-500)
    And el outline está separado del elemento (focus:outline-offset-2)
  
  Scenario: Tab navigation sigue orden lógico
    Given que estoy en el dashboard
    When presiono Tab repetidamente
    Then navego por: header search → filter buttons → lead cards → bottom buttons
    And el orden es left-to-right, top-to-bottom (LTR en español)
    And no hay saltos extraños (tab-index es 0 o positivo, no negativo)
    And puedo volver atrás con Shift+Tab
  
  Scenario: Enter/Space activa botones
    Given que tengo focus en un botón
    When presiono Enter o Space
    Then el botón se activa (onclick se dispara)
    And no hay doble-activación
    And el efecto es el esperado (modal abre, lead se crea, etc.)
  
  Scenario: Escape cierra modales
    Given que hay un modal abierto (CreateLeadModal)
    When presiono Escape
    Then el modal se cierra
    And el focus vuelve al botón que lo abrió ("+  Nuevo Lead")
    And el backdrop desaparece
  
  Scenario: Tab trap en modal (no escapo con Tab)
    Given que el CreateLeadModal está abierto
    When presiono Tab dentro del modal
    Then permanezco dentro del modal (focus no sale)
    And el último elemento tabbable vuelve al primero (circular)
  
  Scenario: Teclado en inputs
    Given que tengo focus en un input (buscar, crear lead)
    When presiono caracteres
    Then se escriben normalmente
    And presionar Enter en search busca (no envía form)
    And presionar Enter en form submit crea lead
  
  Scenario: Drag & Drop accesible con teclado
    Given que E3-S3 (Drag & Drop) está implementado
    When no puedo usar mouse (motricidad limitada)
    Then hay alternativa de teclado
    And puedo usar Status Filter → cambio estado manualmente
    Or puedo doble-click lead para abrir modal + cambiar estado
```

## 🎯 Patrones de Implementación (Del Contexto)

### **Patrón 1: ARIA Labels en Componentes Dinámicos**

```typescript
// ❌ ANTES (sin accesibilidad)
<button onClick={handleClose} className="...">X</button>

// ✅ DESPUÉS (accesible)
<button 
  onClick={handleClose} 
  aria-label="Cerrar modal"
  className="focus:outline-2 focus:outline-blue-500 focus:outline-offset-2"
>
  X
</button>
```

### **Patrón 2: Focus Management en Modales**

```typescript
const CreateLeadModal = ({ isOpen, onClose }) => {
  const firstInputRef = useRef<HTMLInputElement>(null);
  
  useEffect(() => {
    if (isOpen) {
      firstInputRef.current?.focus(); // Focus al input
    }
  }, [isOpen]);
  
  const handleKeyDown = (e: KeyboardEvent) => {
    if (e.key === 'Escape') onClose();
  };
  
  return (
    <div role="dialog" aria-modal="true" onKeyDown={handleKeyDown}>
      <input ref={firstInputRef} aria-label="Nombre del lead" />
    </div>
  );
};
```

### **Patrón 3: i18n Helper**

```typescript
// frontend/src/utils/i18n.ts
const messages = {
  'btn.close': 'Cerrar',
  'lead.new': 'Nuevo',
  'lead.contact': 'En contacto',
  'date.format': 'dd/mm/yyyy',
};

export const t = (key: string): string => messages[key] ?? key;

export const formatDate = (date: Date): string => {
  return new Intl.DateTimeFormat('es-ES', {
    day: '2-digit',
    month: '2-digit',
    year: 'numeric',
  }).format(date);
};

export const formatNumber = (num: number): string => {
  return new Intl.NumberFormat('es-ES').format(num);
};
```

## 🧪 Testing Strategy (Vitest + axe-core)

### **Test File: E6-S3-Accessibility.test.tsx**

```typescript
import { describe, it, expect, beforeEach } from 'vitest';
import { render, screen } from '@testing-library/react';
import userEvent from '@testing-library/user-event';
import { axe } from 'axe-core';
import App from '../App';

describe('E6-S3: Accessibility (WCAG AA)', () => {
  
  // Test 1: No axe violations
  it('should have no accessibility violations', async () => {
    const { container } = render(<App />);
    const results = await axe(container);
    expect(results.violations).toHaveLength(0);
  });

  // Test 2: Keyboard navigation
  it('should navigate with Tab key', async () => {
    const user = userEvent.setup();
    render(<App />);
    
    const searchInput = screen.getByPlaceholderText('Buscar leads');
    expect(searchInput).toBeInTheDocument();
    
    // Tab to search
    await user.tab();
    expect(searchInput).toHaveFocus();
  });

  // Test 3: Escape closes modal
  it('should close modal with Escape', async () => {
    const user = userEvent.setup();
    render(<App />);
    
    const newLeadBtn = screen.getByText('+ Nuevo Lead');
    await user.click(newLeadBtn);
    expect(screen.getByRole('dialog')).toBeInTheDocument();
    
    await user.keyboard('{Escape}');
    expect(screen.queryByRole('dialog')).not.toBeInTheDocument();
  });

  // Test 4: Focus outline visible
  it('should have visible focus outline', async () => {
    const user = userEvent.setup();
    render(<App />);
    
    const button = screen.getByText('+ Nuevo Lead');
    await user.tab();
    
    const computedStyle = window.getComputedStyle(button);
    expect(computedStyle.outlineWidth).not.toBe('0px');
  });

  // Test 5: Contrast
  it('should have adequate color contrast', async () => {
    render(<App />);
```

## 📝 Notes & Considerations

### **Scope Clarifications**

- **E6-S3 cubre:** Accesibilidad fundamental (keyboard, screen reader, contrast, ARIA)
- **Fuera de scope:** Multiidioma completo (solo base ES), RTL support, advanced i18n (plurals, translations, etc.)
- **Heredado funciona:** E6-S1 responsive + E6-S2 animations ya accesibles (prefers-reduced-motion)

### **Common Pitfalls to Avoid**

1. ❌ `tabindex="-1"` on elements that should be focusable
2. ❌ Focus outline removed without replacement (no outline: none!)
3. ❌ Modals without focus trap (user tabs out)
4. ❌ Buttons styled as divs (use semantic `<button>`)
5. ❌ Images/icons without alt text or aria-label
6. ❌ Color as only indicator (add icon/text too)
7. ❌ aria-label on every element (only where text is missing)

### **Screen Reader Testing**

**Windows (Free):** NVDA (https://www.nvaccess.org/)
**Mac (Built-in):** VoiceOver (Cmd+F5)
**Testing Steps:**
1. Open app in screen reader
2. Navigate with Tab / Shift+Tab
3. Verify announcements: headings, labels, roles, states
4. Read error messages
5. Create/edit a lead (full workflow)
