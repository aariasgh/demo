## Developer Context

### Why Code-Splitting Works Here

**Current Problem**:
- All components (modals, widgets) bundled together from app start
- 501.26 kB JS loaded even if user never opens Create Lead modal
- Mobile 3G: ~500 kB ÷ 3 Mbps ≈ 1.3s just for JS download

**Solution**:
- CreateLeadModal (40 kB) loads only when user clicks "C" or "Create"
- QuickNotesModal (20 kB) loads only when user clicks "N"
- Initial load: ~350 kB (core KanbanBoard + routing) ÷ 3 Mbps ≈ 0.9s
- **Total improvement**: 1.3s → 0.9s initial load (30% faster)

### Why These Components?
- **Modal dialogs**: Not needed on app load, only on user action
- **RiskWidget**: Heavy (analytics + charts), loads on demand
- **react-beautiful-dnd**: Large library, can load after KanbanBoard renders

### Why NOT Split?
- **useKeyboardNavigation**: Global listener, needed immediately
- **TanStack Query**: Core to feature, leads fetched on mount
- **Zustand store**: Global state, needed immediately
- **Tailwind CSS**: Already tree-shaken by Vite

### Performance Caveats
- **First lazy-load latency**: Small delay when opening modal first time (~500ms on 3G)
  - Acceptable because user sees LoadingSpinner
  - Second time (cached): instant
- **Source map size**: .map files are 2-3x larger, but NOT shipped to browser
  - Keep for error tracking
  - Remove in production if needed later

## Developer Notes

This story emerged from the "Chunk Size Warning" documented in E6-S3-ACCESSIBILITY-PATCH-COMPLETION.md. The warning indicated that the initial bundle exceeded 500 kB and needed optimization. By implementing React.lazy() code-splitting, we can defer non-critical UI components until first use, reducing initial load from 501 kB to <400 kB.

**Key insight from E6-S3**: The accessibility work established good Suspense boundaries (LoadingSpinner) which are now reused here for lazy-loading fallbacks.

**Developer responsibility**: Ensure that lazy-loading doesn't introduce network waterfalls or cumulative latency that negates the bundle size savings.
