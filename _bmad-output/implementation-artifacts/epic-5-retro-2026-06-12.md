## ⚠️ LOS DESAFÍOS: QUÉ FUE DIFÍCIL

### 1. **Cambios en Especificación Medio Camino (E5-S1)**

**Problema:** Requerimientos no completamente congelados

- Durante E5-S1 development, surgió necesidad de agregar campo "metadata" para contexto de eventos
- Requirió refactor de schema (fortunately menor)
- **Elena:** "Pensé que teníamos todo claro, pero aparecieron cambios de último minuto"

**Lección:** Especificaciones E2E no son garantía de que requerimientos estén congelados. Product owner debe congelar scope explícitamente.

### 2. **Performance Consideration Descubierto Tarde (E5-S2)**

**Problema:** Pagination limit inicialmente muy alto

- Endpoint /api/leads/{id}/audit permitía limit=500
- Concern: A escala (10k leads × 500 events = 5M responses), crash de memory
- **Charlie:** "Lo vimos en code review, pero fue un descubrimiento post-implementation"

**Lección:** Performance constraints deben ser capturadas en especificación de architecture. No esperar a code review.

### 3. **Testing Strategy Inicialmente Incompleta**

**Problema:** Tests no cubrían todos los edge cases de auditoría

- Primera suite de tests faltaba: validación de event_type, paginación edge cases, concurrencia
- Requirió agregar 1 test adicional (test_audit_rejects_invalid_event_type)
- **Dana (QA Engineer):** "Los tests E2E fueron completos, pero los tests unitarios de backend tuvieron gaps"

**Lección:** Test planning debe ser específico a tipo de cambio (E2E ≠ Unit ≠ Integration). No asumir cobertura.

### 4. **Composite Index Added Post-Implementation**

**Problema:** Query optimization fue afterthought, no design-first

- Index (lead_id, created_at DESC) agregado en migration 006 después de code review
- Mejor haberlo planeado antes
- **Charlie (Senior Dev):** "Esto debería estar en la especificación técnica del epic, no descubierto en review"

**Lección:** Query optimization patterns deben ser revisados en architecture phase, no en code review phase.

## 🎯 INSIGHTS CLAVE (Lecciones Aprendidas)

### **Insight #1: E2E Specifications Son Poderosas Pero No Completas**

✅ E5-S1 tuvo especificación E2E excelente y sí mejoró clarity  
❌ Pero especificación E2E no previene cambios mid-development o performance issues  

**Recomendación para próximo epic:** Agregar sección "Performance & Optimization Requirements" a especificación, no dejar para code review.

---

### **Insight #2: Code Review de 3 Capas Detecta Más que Tests**

✅ 3-layer review (Blind Hunter + Edge Case Hunter + Acceptance Auditor) encontró CRITICAL + 2 MEDIUM  
✅ Tests no hubieran capturado estos issues sin explicit edge case testing  

**Recomendación:** Mantener disciplina de 3-layer review. Este proceso funcionó.

---

### **Insight #3: Architecture Decisions Necesitan Explícita Aprobación**

El modelo JSONB para auditoría fue brillante, pero fue decisión de Charlie sin explícita aprobación de equipo.

✅ Funcionó bien esta vez  
❌ Riesgo: Podrías haber elegido architecture incorrecta y pasado mucho tiempo refactorizando

**Recomendación:** Para epics complejos, tener mini "architecture review" checkpoint antes de dev starts.

---

### **Insight #4: Junior Developers Se Desempeñan Mejor Con Especificaciones Congeladas**

Elena (Junior Dev) fue muy productiva en E5-S1 porque especificación fue clara y congelada.  
Elena tuvo fricción en E5-S2 porque auditoría requirements evolucionaron mid-dev.

### **Insight #5: Testing Gaps Se Descubren en Code Review, No Durante Dev**

Los developers (Amelia, Charlie) generaron buenos tests pero no exhaustivos.  
Dana (QA) y 3-layer review encontraron gaps en pensamiento.
