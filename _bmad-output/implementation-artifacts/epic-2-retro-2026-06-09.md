### ✅ E2-S3: Cambiar Estado - API PATCH /leads/{id}/status (8 pts)

**Objective:** Implement backend status transitions with idempotency and safety

**Delivered:**
- PATCH /api/leads/{id}/status endpoint with async handler
- LeadStatus enum with 4 valid values: Nuevo, En contacto, Propuesta enviada, Cerrado
- Status transition rules enforced: any → any (no FSM restrictions for MVP)
- Idempotency support:
  - Client sends `Idempotency-Key` header (UUID)
  - Server caches results by {lead_id}:{idempotency_key}
  - Same key returns same result (prevents accidental double-status-changes)
- Audit trail records status transitions with before/after values
- Error responses: 200 OK, 400 Bad Request, 404 Not Found, 409 Conflict
- 8 unit tests covering status transitions and idempotency
- Full regression suite: 39/39 tests passing (E2-S1 + E2-S2 + E2-S3)

**Code Review:** ✅ Critical Issues Fixed
- **CRITICAL BUG #1: Cache Key Collision**
  - Issue: Cache key only used lead_id, not idempotency_key
  - Impact: Different requests with different keys would collide, returning wrong cached result
  - Fix: Changed cache key to {lead_id}:{idempotency_key}
  - Prevention: Added specific test for cache collision scenario
  
- **CRITICAL BUG #2: Request Parameter Extraction**
  - Issue: Status parameter extracted from URL query instead of request body
  - Impact: PATCH /api/leads/1/status?status=Nuevo worked, but PUT /api/leads/1/status (correct REST) failed
  - Fix: Extract status from request body JSON payload
  - Prevention: Added test for correct REST request structure

- **ISSUE #3: No-op Timestamp Bump**
  - Issue: updated_at timestamp changed even when status didn't change (duplicate request)
  - Impact: Audit trail shows activity that didn't happen
  - Fix: Only update timestamp if status actually changed
  - Prevention: Added test verifying timestamp only updates on real changes

**Testing:** 8/8 tests passing for E2-S3
- Status transition to each of 4 values
- Idempotency caching correctness
- Cache collision prevention
- No-op protection (timestamp only changes on real change)
- Audit trail records status transitions
- 404 for non-existent lead
- Invalid status values rejected

**Regression Testing:** 39/39 total tests passing
- E2-S1: 14 tests still passing ✅
- E2-S2: 17 tests still passing ✅
- E2-S3: 8 new tests passing ✅

**Status:** ✅ Production-ready after critical fixes, unblocks E2-S4 and E3

**Key Learnings:**
1. Idempotency is tricky — cache key MUST include the request identifier, not just the resource
2. Code review's edge case analysis caught concurrency bugs that would be silent in production
3. Timestamp discipline (only update when state changes) prevents false audit entries

### 🟡 CHALLENGES & LEARNING OPPORTUNITIES

#### **Challenge 1: Email Uniqueness Rule Implemented in Multiple Places**

The email uniqueness business rule was implemented in multiple layers:
1. **Database constraint:** Unique index on email column
2. **E2-S1 validation:** POST endpoint rejects duplicate emails (409)
3. **E2-S2 validation:** PUT endpoint allows lead's own email, rejects other leads' emails
4. **E2-S4 async check:** Frontend blur handler calls GET /api/leads/validate-email

**Discussion:**
- **Charlie:** "We have duplication across layers. If the business rule changes, we need to update 4 places."
- **Amelia:** "But that duplication is necessary. Database constraint is for data integrity, E2-S1/S2 is for API validation, E2-S4 is for UX."
- **Dana:** "The real question: do we understand the rule well enough to document it?"

**Resolution:**
- The rule is: **Email must be globally unique EXCEPT when editing a lead can keep its own email.**
- This is implemented correctly across all layers, but wasn't explicitly documented.
- **Action item:** Document complex domain rules in architecture ADR before E3.

---

#### **Challenge 2: Async Form Validation Patterns**

E2-S4's async email validation (blur handler calling GET /api/leads/validate-email) required:
- Proper state management (loading, error states)
- Debouncing (only check if email valid format first)
- Error handling (don't show error on network failure, let server-side validation catch it)
- Testing (mocking async calls, race conditions)

**Impact:** Testing took longer than expected because we didn't have a reusable pattern.

**Resolution:**
- **Action item:** Extract async validation pattern to helper function for reuse in E3+.
- **Pattern documented:** Handle async blur validations with loading state + error state, debounce before calling, fallback to server-side validation on network errors.

---

#### **Challenge 3: Coordinating Backend Endpoint Availability**

E2-S1 defined the GET /api/leads/validate-email endpoint, but it wasn't used until E2-S4 (2 stories later).

**Discussion:**
- **Alice:** "We built an endpoint that wasn't used for 2 stories. Seems wasteful."
- **Charlie:** "On the flip side, defining the API contract early prevented surprises."
- **Amelia:** "Could we have deferred it? Yes. Should we have? That's a trade-off."

**Perspective:** The endpoint-first approach (E2-S1 defines contract, E2-S4 uses it) worked well for coordination but created a 2-story gap. For future epics, the team should:
- Define endpoints that are immediately needed
- Plan for future endpoints but defer implementation

### 🎯 KEY INSIGHTS FOR FUTURE EPICS

**Pattern 1: Code Review Finding Categories Shift by Layer**
- **Layer 1 (Infrastructure/Backend):** Correctness (validation rules, database constraints)
- **Layer 2 (Backend APIs):** Concurrency (race conditions, caching, idempotency)
- **Layer 3 (Frontend):** UX/Accessibility (focus management, keyboard navigation)

**Implication:** Code review checklists should adapt based on the layer being reviewed.

---

**Pattern 2: Async Operations Are Increasingly Hard Going Up the Stack**
- **Database layer (E2-S1):** Async/await is straightforward in FastAPI
- **Backend caching (E2-S3):** Idempotency + concurrency required careful thinking
- **Frontend validation (E2-S4):** Browser async with React hooks + form state was most complex

**Implication:** Expect longer review cycles for higher-layer async work. Plan accordingly.

---

**Pattern 3: Testing Grows With Confidence**
- Early tests (E2-S1): Basic scenarios
- Middle tests (E2-S2, E2-S3): Edge cases caught by code review
- Late tests (E2-S4): Comprehensive test coverage because we learned from reviews

**Implication:** Test quality improves through the epic as team learns patterns. Consider backfilling early tests after epic completes (optional).
