## 🎯 STORY REQUIREMENTS

### User Story Statement

**Como** desarrollador frontend,  
**quiero** un endpoint GET /api/leads que entregue la lista de leads con filtros y paginación,  
**para que** el tablero Kanban pueda renderizar los leads sin depender de datos hardcoded.

### Business Value

- ✅ El Kanban necesita datos reales de leads para mostrar el pipeline.
- ✅ Los filtros por estado y la paginación evitan sobrecargar la UI.
- ✅ El endpoint debe responder rápido para cumplir el SLA de performance.
- ✅ La interfaz debe reutilizar el mismo contrato de datos definido por la arquitectura y los tests existentes.

## ✅ ACCEPTANCE CRITERIA (BDD)

```gherkin
Feature: Listar Leads - API Backend

  Scenario: Obtener todos los leads
    Given que existen 50 leads en la base de datos
    When hago GET a "/api/leads"
    Then recibo status 200 OK
    And la respuesta contiene un array de leads
    And cada lead incluye id, name, company, email, status, created_at, updated_at

  Scenario: Filtro por status
    Given que existen leads en varios estados
    When hago GET a "/api/leads?status=Nuevo"
    Then recibo únicamente los leads con status "Nuevo"

  Scenario: Paginación funciona
    Given que existen 100 leads
    When hago GET a "/api/leads?limit=20&offset=0"
    Then recibo 20 leads
    And la respuesta incluye metadata total, limit y offset

  Scenario: Ordenamiento por fecha
    Given que existen múltiples leads
    When hago GET a "/api/leads"
    Then los resultados llegan ordenados por created_at DESC

  Scenario: Performance dentro del SLA
    Given que existen 50 leads
    When consulto el endpoint
    Then el tiempo de respuesta p95 es menor a 100 ms
```

## 💻 TECHNICAL REQUIREMENTS

### Implementation Context

The backend already has the lead data model, schemas, and CRUD endpoints in:

- backend/app/routers/leads.py
- backend/app/schemas/lead.py
- backend/app/models/lead.py
- backend/tests/test_leads_create.py
- backend/tests/test_leads_update.py
- backend/tests/test_leads_status.py

This story must extend the existing async FastAPI + SQLAlchemy pattern without breaking the current CRUD behavior.

### Required Changes

1. Add GET /api/leads in backend/app/routers/leads.py.
2. Support query parameters:
   - status: optional filter
   - limit: default 100, maximum 1000
   - offset: default 0
3. Return a response contract aligned with the architecture:
   - data: list of lead records
   - meta: { total, limit, offset }
4. Sort results by created_at DESC.
5. Preserve the current lead field set and avoid exposing internal-only attributes.
6. Use the same error-handling style already used in the existing lead endpoints.

### Guardrails for the Developer

- Reuse the existing AsyncSession dependency from app.database.
- Follow the current async / SQLAlchemy query style already used in create/update/status endpoints.
- Avoid N+1 queries; fetch leads in a single query.
- Keep the endpoint read-only and simple, because the idempotency review for E3-S1 explicitly notes that no idempotency protection is required for GET operations.
- Prefer the existing Pydantic response model pattern over introducing a parallel response format.

### Files Likely to Change

- backend/app/routers/leads.py
- backend/app/schemas/lead.py (only if a dedicated list response schema is needed)
- backend/tests/test_leads_list.py (new test suite)
