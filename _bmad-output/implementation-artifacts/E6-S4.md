# E6-S4: Keyboard Navigation & Shortcuts for Kanban

**Story Status:** 🟢 **READY FOR DEVELOPMENT**

**Completion Note:** Ultimate context engine analysis completed - comprehensive developer guide created

---

## 📋 Story Summary

Complete keyboard navigation for the Kanban board and implement keyboard shortcuts for common actions. This story builds on E6-S3 accessibility work (focus management, ARIA attributes, semantic HTML) to provide power users and accessibility-first users with efficient keyboard-driven workflows.

**Business Value:**
- Users with motor impairments can operate the system without a mouse
- Power users can move leads faster using keyboard than mouse
- Improves accessibility score (WCAG AA Level 2)
- Reduces repetitive strain from mouse-heavy workflows

**User Story:**

As an **accessibility-first user** or **power user with keyboard preference**,  
I want to **navigate and manipulate leads entirely via keyboard** (Tab, Arrow keys, Enter/Space, Escape),  
so that I can **work efficiently without a mouse and reduce repetitive strain**.

## 🎯 Acceptance Criteria

### AC-1: Tab Navigation Between Kanban Columns

**Dado** que estoy en el Kanban board,  
**Cuando** presiono Tab repetidamente,  
**Entonces** el foco se mueve secuencialmente: Nuevo column → En contacto → Propuesta → Cerrado (y cicla de vuelta a Nuevo)

**Detalles Técnicos:**
- Each column header should be focusable (tabindex="0" or semantic button)
- Visual focus ring with `outline-2 outline-blue-500 outline-offset-2`
- Focus order left-to-right matches visual layout
- First Tab from Kanban board lands on "Nuevo" column header

**Test Scenario:**
- User presses Tab 5 times from page start → should land on Cerrado, then back to Nuevo
- Each column has visible focus indicator

### AC-2: Arrow Keys to Navigate Within a Column

**Dado** que tengo el foco en una columna (column header or inside),  
**Cuando** presiono ↓ (Down Arrow),  
**Entonces** el foco se mueve al primer lead card en esa columna (o siguiente card si ya seleccionado)

**Dado** que tengo el foco en un lead card,  
**Cuando** presiono ↑ (Up Arrow),  
**Entonces** el foco se mueve al lead card anterior en la misma columna

**Detalles Técnicos:**
- Column headers are not focusable for arrow navigation (only Tab-focusable)
- Lead cards within a column are in a linear tab order (Tab key moves through all cards)
- Arrow Up/Down cycles through cards in same column
- Arrow Left → moves to column on the left (and first card in that column if exists)
- Arrow Right → moves to column on the right (and first card in that column if exists)
- Visual focus ring on lead cards

**Test Scenario:**
- User navigates to "Nuevo" column via Tab
- Presses ↓ to focus first lead
- Presses ↓ to focus second lead
- Presses ← to move to "Búsqueda/Filtro" region (search bar)
- Presses → multiple times cycles through columns

### Architecture Compliance

**Pattern: Keyboard Shortcut Centralization**
- All shortcuts defined in `frontend/src/utils/keyboardConfig.ts`
- Registered globally in `App.tsx` or `KanbanBoard.tsx` wrapper
- Each handler dispatches Zustand action or direct component event
- No hardcoded key listeners scattered in components

**Pattern: Focus Management**
- Use React `useRef` to track previously focused element
- Before opening modal: save `previousFocus = document.activeElement`
- After closing modal: `previousFocus?.focus()`
- Focus trap via focus-trap-react library (already used in E6-S3)

**Pattern: Accessible Focus Styles**
- Consistent Tailwind classes: `focus-visible:outline-2 focus-visible:outline-blue-500 focus-visible:outline-offset-2`
- Never remove focus outline (no `outline: none`)
- Use `:focus-visible` pseudo-class (only show ring on keyboard, not mouse)

**Pattern: ARIA Labels for Keyboard Hints**
- Lead card: `aria-label="[name] de [company], estado [status]. Enter para abrir, S para cambiar estado"`
- Buttons: `aria-label="Crear Lead (Shortcut: C)"`
- Help text via `aria-description` if needed

## 📝 Dev Notes for Amelia

1. **Global Keyboard Registration Pattern:**
   ```typescript
   // In useKeyboardNavigation.ts
   useEffect(() => {
     const handleKeyDown = (event: KeyboardEvent) => {
       if (event.key === 'c' && !event.ctrlKey && !event.altKey) {
         event.preventDefault()
         openCreateLeadModal()
       }
       if (event.key === '?' && !event.ctrlKey) {
         event.preventDefault()
         openHelpModal()
       }
     }
     
     document.addEventListener('keydown', handleKeyDown)
     return () => document.removeEventListener('keydown', handleKeyDown)
   }, [])
   ```

2. **Focus Management Pattern:**
   ```typescript
   const previousFocus = useRef<HTMLElement | null>(null)
   
   const openModal = () => {
     previousFocus.current = document.activeElement as HTMLElement
     setModalOpen(true)
   }
   
   const closeModal = () => {
     setModalOpen(false)
     previousFocus.current?.focus()
   }
   ```

3. **Avoid Keyboard Shortcut Conflicts:**
   - Single letters (C, N, S, F, R) might conflict with browser/screen reader commands
   - Fallback: use Alt+C, Alt+N, Alt+S if single letter doesn't work
   - Test in different browsers (Chrome, Firefox, Safari)

4. **Screen Reader Compatibility:**
   - aria-label: "lead name, status, [keyboard hints]"
   - Use aria-description for longer help text
   - Test with NVDA or screen reader browser extension

5. **Focus Outline Consistency:**
   - All interactive elements must use same focus classes
   - Never remove outline (no `outline: none`)
   - Use `:focus-visible` for keyboard-only focus rings

6. **Testing Approach:**
   - Start with unit tests for keyboard hooks
   - Then component tests for focus navigation
   - Finally, manual keyboard-only E2E workflow
   - Don't skip screen reader testing - use NVDA for final validation
