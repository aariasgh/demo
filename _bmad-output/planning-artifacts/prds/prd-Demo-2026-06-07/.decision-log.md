# Decision Log: Mini CRM de Seguimiento de Clientes Potenciales

This file tracks all decisions, assumptions, overrides, and rationale made during PRD development. It serves as the audit trail for understanding why the PRD is structured the way it is.

---

## Decisions Made (2026-06-07)

### D-1: Authentication Method
**Decision:** Login hardcoded (uno usuario demo: `user: demo, password: demo123`)  
**Rationale:** Para demo, autenticación simple es suficiente. Reduce complexity, enfoca en features del Mini CRM.  
**Alternative Considered:** Multi-factor auth, OAuth — rechazado por overkill para demo.  
**Owner:** Anuar (Consultor)  
**Date:** 2026-06-07  
**Status:** Approved  

---

### D-2: Frontend Stack
**Decision:** React + Next.js + Tailwind CSS  
**Rationale:** Stack moderno, componentes reutilizables, CSS in utility-first (rápido para UI responsiva).  
**Evidence:** Alineado con project-context.md.  
**Owner:** Anuar (Consultor)  
**Date:** 2026-06-07  
**Status:** Approved  

---

### D-3: "Leads en Riesgo" Implementation
**Decision:** Widget en header que muestra count + link a filtro (no columna separada, no toast)  
**Rationale:** Widget es minimal pero visible. No crea "ruido" visual, no requiere popup. Filtro es actionable.  
**Alternative Considered:** Columna separada (clutters Kanban) — rejected. Toast en login (intrusive, user dismisses) — rejected.  
**Owner:** Anuar (Consultor)  
**Date:** 2026-06-07  
**Status:** Approved  

---

### D-4: Multi-User Scope
**Decision:** Single session shared — todos los usuarios ven los mismos cambios en tiempo real, sin aislamiento  
**Rationale:** Para demo de 8 junio, scope simple es correcto. Multi-user real es post-MVP.  
**Note:** Arquitectura prepara para multi-user (timestamps, audit trail), pero permisos/aislamiento not implemented V1.  
**Owner:** Anuar (Consultor)  
**Date:** 2026-06-07  
**Status:** Approved  

---

### D-5: Real-Time Sync Strategy
**Decision:** Polling (2-3s interval) en lugar de WebSockets  
**Rationale:** Para demo, polling es suficiente y más simple. WebSockets es overkill para este scope.  
**Trade-off:** Latency ~2-3s vs. <100ms con WS. Aceptable para demo.  
**Owner:** John (PM) + Dev Team (TBD)  
**Date:** 2026-06-07  
**Status:** Tentative (a confirmar con arquitecto)  

---

### D-6: Email Validation
**Decision:** Email debe ser único pero NO validado (sin envío de confirmación)  
**Rationale:** Para demo, verificar unicidad es suficiente. Full email validation es post-MVP.  
**Owner:** Anuar (Consultor)  
**Date:** 2026-06-07  
**Status:** Approved  

---

### D-7: Test Coverage Target
**Decision:** >70% cobertura (no 100%)  
**Rationale:** 70% cubre los paths críticos (CRUD, estado transitions, validaciones). 100% es perfectionism innecesario para demo.  
**Owner:** John (PM) + QA Team (TBD)  
**Date:** 2026-06-07  
**Status:** Approved  

---

### D-8: Scope Exclusions
**Decision:** Out of scope: reportes, integraciones email, multi-team, mobile app, importación CSV  
**Rationale:** Estos son nice-to-haves post-demo. MVP es disciplinado: solo lo esencial.  
**Owner:** Anuar (Consultor)  
**Date:** 2026-06-07  
**Status:** Approved
